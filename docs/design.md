# 架构与设计说明 · 直招好工作

本文说明「为什么这样设计」，以及关键取舍背后的理由。接口细节见 [api.md](api.md)。

---

## 1. 系统边界与核心概念

**直招**在本系统中是一个可验证的判定，而不是一个营销词：

| 概念 | 落地方式 |
|---|---|
| 官网《加入我们》链接 | `companies.careers_url` + `discovery_url`（记录从哪个页面发现的） |
| 直招岗位 | `job_postings.source_url`（岗位详情页 URL，唯一）+ `is_direct_hire` |
| 可追溯 | 每个岗位保留来源站点、来源页面上标注的公司名、抽取器、解析置信度、原始结构化数据 |

因此系统能回答：「这个岗位是谁发布的、从哪个页面抓来的、什么时候抓的、改过什么」。

## 2. 分层与目录职责

```
HTTP 层        internal/server/{router,middleware,handler}
  ↓ 只做参数绑定、鉴权、响应封装
业务层         internal/service
  ↓ 事务、状态流转、视图组装、审计
数据/能力层    internal/{ent,crawler,auth,casbin,mail,store,scheduler}
```

分工原则：

- **handler 不含业务判断**。例如「驳回必须填原因」写在 service，而不是 handler 里，
  这样定时任务、脚本、未来的 gRPC 入口复用同一套规则。
- **service 直接使用 ent**，没有额外引入 repository 层。数据访问逻辑本身不复杂，
  多加一层只会增加跳转成本。
- **crawler 是纯能力层**：输入 URL 与站点规则，输出结构化岗位，**不碰数据库**。
  这样它可以脱离环境单测（`internal/crawler/scope_test.go` 即为明证）。
- **bootstrap 统一装配**，`cmd/{api,worker,seed}` 三个入口共享同一套初始化，
  不会出现「某个入口忘了建表或播种配置」的环境差异。

## 3. 数据模型

10 张表，职责严格分离：

```
companies ──1:N──> job_postings ──1:N──> job_revisions
    │                   │
    │                   └──N:1──> users（审核人）
    └──1:N──> crawl_runs ──1:N──> crawl_logs

users ──N:M(经 casbin_rule 的 g 规则)──> 角色
settings / audit_logs / verification_codes 独立
```

### 3.1 岗位的「三个时间」刻意分开

这是本项目最容易踩坑的地方。一个字段不可能同时表达三件事：

| 字段 | 语义 | 何时刷新 |
|---|---|---|
| `published_at` | 来源页面标注的**发布时间** | 抓取到该信息时 |
| `last_updated_at` | 本系统感知到的**内容最后变更时间** | 内容指纹变化时 |
| `last_seen_at` | 最近一次抓取时该岗位**仍在架** | 每次抓取都刷新 |

只有区分开，才能回答「这个岗位是三天前新发的，还是三个月前发的但今天还在挂」。
`last_seen_at` 也是判定下线的依据（连续 `job_expire_after` 未出现 → 置为 `expired`）。

### 3.2 内容指纹与修订记录

`content_hash` 由 **规范化字段集**（`contentFields`）算出。关键设计：

> 抓取结果与数据库实体都先转换成同一个 `contentFields`，再计算指纹与比对。

这样「爬虫入库」与「人工编辑」两条写入路径的变更判定口径完全一致，
不会出现「爬虫认为没变、人工编辑认为变了」的分裂。

指纹刻意排除噪声字段（`crawled_at`、`parse_confidence`、`raw_json` 等），
否则每次抓取都会被误判为内容更新，`last_updated_at` 也就失去意义。
内容变化时写入 `job_revisions`（变更字段列表 + 快照 + 触发方 + 操作人），
于是「最后更新时间」背后永远有一条可查的原因。

### 3.3 实质性变更退回审核

已发布岗位发生**实质性变更**（标题、任职要求、岗位职责、薪资、用工性质、城市、地址）时，
自动退回 `pending_review`；而补充简介、加标签这类变更只留痕、不打扰审核流程。

理由：薪资与要求一变，之前的人工审核结论就不再成立；而如果任何微小改动都退回审核，
审核队列会被噪声淹没，最终谁都不看。

状态机：

```
                  ┌──────────────┐
   抓取到新岗位 →  │ pending_review│ →(驳回)→ rejected ─┐
                  └──────┬───────┘                     │
                         │(通过)                        │(改判/重新出现)
                         ↓                             │
                    approved ←──────┐                  │
                         │          │(重新上线)         │
                    (下线)↓          │                  │
                     offline ───────┘                  │
                         │                              │
              (长期未再出现)↓                            │
                      expired ←─────────────────────────┘
```

## 4. 授权设计：为什么 Casbin 是唯一事实来源

系统需要三种预设角色（管理员 / 审核员 / 用户），且未来要能在线调整权限。

**问题**：如果既在业务表里存 `user.role`，又在 Casbin 里存 `g` 规则，
就会有两份可能互相矛盾的授权数据——这是权限系统最常见的故障源。

**决策**：

- `casbin_rule` 表中的 **p 规则**（谁能访问哪个接口）与 **g 规则**（谁是什么角色）
  是授权的**唯一**事实来源；
- 数据库 `roles` 表**只承载展示元数据**（中文名、描述、层级、是否内置），不参与判定；
- 角色继承通过 g 规则表达：`admin ⊃ reviewer ⊃ user`，避免为每个角色重复写一遍权限。

配套实现：

- 自研 PostgreSQL 策略适配器（`internal/casbin/adapter.go`），只依赖一张扁平表，
  不受第三方 ORM 适配器版本约束；
- 匹配使用 `keyMatch2` 支持路径参数：`/api/v1/jobs/:id/review`；
- 多实例部署时策略每 60 秒自动从数据库重载；
- 用户列表里的角色通过 `GetRolesForUser`（内存计算，无额外查询）获得。

### 为什么接口级鉴权放在路由分组上

存在公开只读接口（岗位列表、岗位详情、字典）。把鉴权做成全局中间件会导致两种坏结果：
要么公开接口被迫登录，要么到处写白名单。因此鉴权挂在分组上：

```
api            ← 公开（含 auth 组，逐接口限流）
api + Auth + RequireAuth + Authorize   ← /me/*
api/admin + Auth + RequireAuth + Authorize ← 管理端
```

`Auth` 中间件刻意设计为「**无令牌不拦截**」：解析失败只清空上下文并继续，
由 `RequireAuth` 统一返回 401。这样同一套中间件既能服务公开接口，也能保护受保护接口。

## 5. 认证与会话

| 决策 | 理由 |
|---|---|
| 访问令牌用 JWT，但校验时**额外查 Redis** | 纯无状态 JWT 无法实现「立即登出」。这里用一次 pipeline（会话是否存在 + 密码版本是否一致）换来登出、改密、禁用、角色变更全部立即生效 |
| 刷新令牌是随机串，Redis 只存 SHA-256 | 库被读取也无法直接冒用；刷新时一次性轮换，旧令牌立即作废 |
| 密码版本（`pwdv`）递增机制 | 改密/重置/禁用/改角色后，所有既有访问令牌立刻失效，无需维护黑名单 |
| 改密后**换发当前设备令牌** | 密码版本递增会连当前设备一起失效。若直接返回成功，用户会被自己踢下线——这是最容易忽略的体验缺陷 |
| 账号不存在时也执行一次 bcrypt | 抵御通过响应时间枚举已注册邮箱 |
| 验证码只存 HMAC 摘要且绑定邮箱+用途 | 摘要泄漏也无法跨账号、跨用途复用；数据库留审计但不存明文 |
| 找回密码始终返回同一话术 | 不暴露某邮箱是否已注册 |

登录失败计数 + 临时锁定用于抵御在线撞库；`bcrypt` 只处理前 72 字节，
因此超长密码在入口直接拒绝，而不是被静默截断（截断会让「后 72 字节」失去意义）。

### 5.1 邮件配置为什么可以在线改，以及怎么改才安全

邮件（注册验证码、密码重置通知）是认证链路的一部分。若只能改配置文件，
每换一次 SMTP 供应商都要登服务器改文件并重启——运维成本高，且容易在重启窗口里丢掉登录能力。
因此配置被搬到后台，但带来三组必须解决的问题：

**① 保存后如何立即生效？**
投递器在启动时就被 `Services` 持有，直接替换字段会引起数据竞争。
这里用一个带读写锁的包装器 `mail.Dynamic` 承载「当前生效的实现」，
保存成功后原子替换。这与 `crawler.SetScope` 是同一思路：
把「可变的运行时参数」与「不变的依赖图」解耦，就不必为一处配置改动重启整个进程。

**② SMTP 密码怎么存？**
明文入库是不可接受的（备份、日志、只读账号都可能泄漏）。
密码用 **AES-256-GCM** 加密后落库，密钥由 `jwt.secret` 通过 SHA-256 派生并做用途隔离
（`secret.DeriveKey(master, "mail-smtp")`）。选 GCM 而非 CBC 是因为它自带完整性校验：
密文被篡改会直接解密失败，而不是解出一段乱码被当成合法密码去连服务器。
代价是更换 `jwt.secret` 会导致已存密码失效——这是**刻意**的取舍：宁可要求重填，也不留明文后门。

**③ 接口怎么既让管理员看到状态，又不泄漏口令？**
读接口永远返回占位符 `********` 与 `has_password` 布尔值，明文不出服务端。
写接口对密码字段实现三态语义：

| 提交内容 | 行为 | 解决的问题 |
|---|---|---|
| 新密码 | 更新 | 正常修改 |
| 空字符串 / 原样回传占位符 | 沿用旧密码 | 前端不知道明文，若把「空」当成「清空」就会误删凭据 |
| `clear_password: true` | 显式清空 | 需要清空时有明确手段，不依赖提交空串 |

审计明细只记录主机、端口、发件人与「密码是否变化」，绝不写入口令本身。

此外提供 **发送测试邮件** 接口：不真的发一封信，管理员无法确认 host/port/TLS/授权码
究竟哪一项填错。测试失败返回 `503` 并带出底层原因（如 `connection refused`），
这一条让「配置排查」从翻日志变成点一下按钮。

## 6. 爬虫设计

### 6.1 合规是功能的一部分

| 机制 | 实现位置 |
|---|---|
| 标准 AI 机器人身份头（UA / From / X-Robot-*） | `crawler/identity.go`，**每个出站请求**（含 robots.txt）都携带 |
| 中文用途说明按 RFC 3986 百分号编码 | `headerValue()`——HTTP 头只允许可见 ASCII，否则部分服务器直接 400 |
| 遵循 robots.txt | `crawler/robots.go`，带 TTL 缓存；404 放行、401/403 拒绝、5xx 保守拒绝 |
| 采纳站点 `Crawl-Delay` | 与配置延时取最大值，经 `SetHostDelay` 注入按域名的节奏控制 |
| 尊重 `noai` / `nogptbot` | `DetectNoAI()` 检查 meta 与 `X-Robots-Tag`，命中即放弃该页 |
| 限速 | 同域名串行 + 固定延时 + 随机抖动 + 每主机并发上限 |
| 指数退避重试 | 只重试网络错误与 408/429/5xx；429 遵守 `Retry-After` |
| 单实例抓取 | Redis 分布式锁 + Lua 脚本安全释放（避免超时后误删他人锁） |
| 入口探测有界 | 最多探测 12 个页面，不把官网整站爬一遍 |

### 6.2 采集链路

```
官网首页/招聘入口
   ↓ locateCareers：有界 BFS（首页 → 关于/联系等候选页）
《加入我们》链接（careers_url）
   ↓ 抓取列表页
岗位链接（FindJobLinks：站点规则优先，否则结构启发式打分）
   ↓ 逐个抓取详情页
字段抽取（分层：JSON-LD → 站点规则 → DOM 启发式）
   ↓ 白名单过滤 + 质量打分
落库 → 待审核
```

分层抽取的取舍：**JSON-LD 优先**（`schema.org/JobPosting`，字段最准，置信度 0.9），
其次站点自定义选择器（0.85），最后通用 DOM 启发式（0.6）。
`extractor` 与 `parse_confidence` 落库，运营能一眼看出某条岗位是「结构化数据很规范」
还是「猜出来的」，从而决定是否信任。

**静态优先 + 无头兜底**：静态正文长度低于阈值时自动切换 chromedp 渲染。
无头浏览器缺失只降级为纯静态抓取并告警，不阻塞服务启动。
`crawl_rules.force_headless` 用于必须渲染的 SPA——该开关在编排层判定
（Fetcher 是全局单例，而规则是每公司一份，放在 Fetcher 里永远不会生效）。

### 6.3 收集范围：静态配置 + 数据库覆盖

需求是「通过配置信息规定爬虫收集工作的类型和行业」。设计成两层：

1. `configs/config.yaml` 的 `crawler.scope` —— 默认基线，随代码走
2. 数据库 `settings['crawler.scope']` —— 管理员在线调整，**逐字段覆盖基线**

合并逻辑在 `SettingService.CrawlScope()`，调度层每次抓取前读取并注入爬虫，
因此改完配置**下一次抓取立即生效，无需重启**。

白名单语义经过刻意打磨：行业**无法判断时放行**（交由人工审核），
而不是一律拒绝——否则大量没标注行业的合规岗位会被误杀，这是采集类系统最常见的数据损失。

## 7. 抓取结果落库

以 `source_url` 为唯一键做三态判定：

| 情况 | 处理 |
|---|---|
| 不存在 | 新建，`status=pending_review`，`revision=1`，写初始修订记录 |
| 指纹相同 | 只刷新 `last_seen_at` / `crawled_at`（**不动 `last_updated_at`**） |
| 指纹不同 | 应用新值、`revision+1`、写修订记录；已发布岗位遇实质性变更则退回待审核 |

并发插入同一 URL 时唯一约束会失败，此时视为「已存在」而不报错——
定时任务与手动触发可能同时命中同一岗位。

抓取过程的可观测性：`crawl_runs` 记录统计口径（发现/新建/更新/未变/过滤/过期），
`crawl_logs` 逐条记录阶段与原因。**被过滤的岗位也会留下原因**，
这样运营能回答「为什么某个岗位没被收录」，而不是面对一个空列表。

## 8. 错误契约

业务错误码分段（详见 [api.md](api.md) 第 11 节）：

```
0      成功
1xxxx  通用（参数、鉴权、限流）
2xxxx  认证与账号
3xxxx  公司 / 岗位 / 审核
4xxxx  爬虫
5xxxx  系统配置
```

- service 层返回 `*apperr.Error`，HTTP 状态码由**错误码分段推导**，不散落在各处
- 非业务错误统一降级为 `10007` 并记录完整错误链，**不把底层实现细节暴露给客户端**
- 5xx 才记录 error 级日志，避免把业务拒绝写成告警噪声
- 所有响应带 `request_id`，与日志串联

## 9. 可观测性与审计

- **审计留痕**：所有会改变系统状态的操作（含抓取、审核、配置、角色）都写 `audit_logs`，
  记录操作者、IP、UA、方法、路径、新旧值。
  审计写入使用 `context.WithoutCancel` + 独立超时，**请求被取消也不会丢审计**，
  且审计失败绝不导致业务失败。
- **抓取留痕**：运行记录 + 明细日志，含每步 URL 与耗时。
- **健康检查**：`/healthz` 汇总 PostgreSQL、Redis、爬虫开关与策略规模。

## 10. 已知边界

| 边界 | 现状 | 后续方向 |
|---|---|---|
| 登录态招聘后台 | 不支持 | 需引入凭据托管与安全存储 |
| 重 XHR 的 SPA | 只等 load 事件 + 可配置等待时长 | 引入 networkIdle 判定 |
| brotli 响应 | 出站收窄为 `Accept-Encoding: gzip`（标准库无法解 br） | 引入 brotli 解码库 |
| 境外/非常规地址 | 可能只解析到 `address`，省市留空 | 扩充地名库 |
| 多副本策略实时性 | 60 秒自动重载 | 用 Redis Pub/Sub 推送变更 |
| 岗位质量评估 | 基于信息完整度打分 | 可引入语义去重与重复岗位聚类 |

## 11. 验证方式

- **单元测试**：`internal/auth`（密码强度、令牌签发/篡改/过期、验证码摘要与 Redis 集成）、
  `internal/crawler`（身份头、收集范围过滤、类别推断、质量评分）。
  Redis 不可用时集成用例自动跳过，**不伪装通过**。
- **端到端冒烟**：`tests/smoke.ps1`（149 项断言）覆盖
  未鉴权拦截 → 注册/登录/刷新/找回密码 → 公司录入 → 自动定位《加入我们》→
  真实抓取模拟企业官网 → 字段抽取校验（任职要求/联系方式/地址/发布时间/薪资）→
  白名单过滤 → 幂等重抓 → 审核发布 → 公开可见性 → 人工编辑与退回审核 →
  RBAC 越权拦截 → 收集范围热更新 → 审计留痕 → 登出失效，并在结尾清理测试数据。
  夹具站点位于 `tests/fixtures/site`，同时提供 JSON-LD 与纯 DOM 两类岗位页，
  用于分别验证两条抽取路径。
